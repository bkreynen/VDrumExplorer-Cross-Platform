## 1. Method — how the embedded schemas work (verified in repo)

- Embedded schemas live in `VDrumExplorer.Model/SchemaResources/<Module>/` — `TD17`, `TD27`, `TD07`, `TD50`, `TD50X`, `AE01`, `AE10` + `Shared/` (verified with `ls`). Each module has a root `<Name>.json` plus `Physical/` (address-mapped containers), `Logical/` (tree), `VEdit/`, and `InstrumentGroups.json` subtrees.
- Loader: `VDrumExplorer.Model/ModuleSchema.cs` static ctor registers every module via `AddSchema(ModuleIdentifier, params int[] additionalSoftwareRevisions)` → `JsonLoader.FromAssemblyResources(...).LoadResource(resourceName, softwareRevision)`. Root resource name is `{Name}.json` (name = identifier minus hyphen, e.g. `TD17.json`).
- **Versioning registration (verified, `ModuleSchema.cs` lines 32–51):**
  - `AddSchema(ModuleIdentifier.TD17, 0x01, 0x02);` → TD-17 schemas registered at software revisions **0x00 / 0x01 / 0x02** (0x00 from `ModuleIdentifier.SoftwareRevision`, 0x01 and 0x02 as additional).
  - `AddSchema(ModuleIdentifier.TD27, 0x02);` → TD-27 at 0x00 and 0x02. Others single-revision.
  - `TD17.json` lines 7–9 confirm: `(revision:0x0)softwareRevision / (revision:0x1) / (revision:0x2)` all in the same root file.
- **"TD-17 v2" = the same `SchemaResources/TD17/TD17.json` loaded at software revision 0x02.** There is no separate v2 file set. Firmware-conditional containers are expressed with `(revision:0x02)` keys on individual fields/containers and `revision:` keys inside field JSON, expanded by the JSON loader.
- Shared machinery: `$resource:` refs, `repeat` (items/indexVariable/gap) expansion, `overlay` (switch-driven field lists, e.g. MFX and V-Edit), `valuesByNumber` enums.

**What rev 0x02 adds over 0x00/0x01 (verified in the schema files):**

| Change | Where | Verified in |
|---|---|---|
| New container **KitReverb**, offset 0x04_00, size 0x0e (11 fields: on/off, Type ×5, Pre delay, Time, Density, Diffusion, LF/HF damp, Spread, Tone, Level) | `Physical/Kit.json` (container `revision: 0x02`, offset `0x04_00`) + `Physical/KitReverb.json` | ✅ |
| New container **KitMasterComp**, offset 0x05_00, size 0x17 (on/off, Type ×8, Split freq, Lo/Hi gain, Lo/Hi threshold, Lo/Hi ratio, Lo/Hi knee, Lo/Hi attack, Lo/Hi release, Balance) | `Physical/Kit.json` + `Physical/KitMasterComp.json` | ✅ |
| **Reverb Send Level** field appended to KitUnitCommon; container size **0x18 → 0x1c** | `Physical/KitUnitCommon.json` lines 2–3 (`(revision:0x00,0x01)size: 0x18`, `(revision:0x02)size: 0x1c`) + `revision: 0x02` Reverb Send Level field | ✅ |
| **11 extra MFX types** (Equalizer, Spectrum, Low Boost, Enhancer, Humanizer, Slicer, Step flanger, Hexa-chorus, 4Tap pan delay, Enhancer → flanger, Speaker sim) | `Physical/KitMfx.json` — 41 values total (0–40), 11 marked `(revision:0x2)` | ✅ |

## 4. HEADLINE RESULT — TD-17 v2 diff: **zero section-level gaps**

## 5. Issue-ready gap bullets (actionable items)

These are the remaining real gaps, suitable as issue text:

1. **(a) Functions with no SysEx address → not remotely controllable; document as limitation.**
   Click/coach functions, user-sample management, and MIX-VOL-style monitor functions have no SysEx address in the TD-17 MIDI Implementation — they are panel-only. Suggested issue: "TD-17: document non-MIDI-controllable functions (click/coach/user samples) in the UI so users know why they can't be edited remotely." *(Inference from doc coverage; flagged.)*
2. **(b) TrigMisc 0x00–0x1F: 32 undocumented bytes → reverse-engineering opportunity.**
   Roland's map leaves offsets 0x00–0x1F of TrigMisc blank; the schema models them as 8 `placeholder32` fields (`TrigMisc.json`). Suggested issue: "TD-17: probe/document TrigMisc 0x00–0x1F (32 undocumented bytes) via hardware experiments — candidate for schema extension."
3. **(c) MFX per-type field semantics spot-check unverified.**
   The MFX overlay params are stored as raw 4-byte fields whose per-type meaning comes from the shared `MultiFx/*.json` field lists. The prior agent flagged these as needing a spot-check against the docs or real hardware (the v2 map dump this session confirms per-type tables exist in §3 — e.g. MFX Type: CHORUS, SPACE-D, AUTO PAN each with their own offsets — but the shared overlay JSONs were not re-verified field-by-field here). Suggested issue: "TD-17: spot-check MFX per-type parameter semantics (Shared/MultiFx overlays) against MIDI Implementation §3 / hardware."

## 6. Phase-0 Task-4 aside — TD-17 kit-change notification (feeds Phase-2 device-feedback design)

**Doc-based answer (verified this session against `TD-17_MIDI_Imple_eng04_W.pdf` §2 Transmit Data):**

> "● Program Change … * Not transmitted when [SETUP]-[MIDI]-[BASIC] Program Change TX is set to 'OFF.' * When a drum kit is selected, the corresponding program number is transmitted."

(TD-27 equivalent, `TD-27_MIDI_Imple_eng03_W.pdf`: "Not transmitted when [SYSTEM]-[MIDI]-[BASIC] Program Change TX is set to 'OFF.'"; TD-50X has an equivalent Program Change TX gate too.)

**Design implication for kit-change detection:**

- **Primary: event-driven via Program Change listener.** The module transmits PC 0–99 (prog.1–100) on the pad/control channel whenever the user selects a kit on the panel — provided **[SETUP]-[MIDI]-[BASIC] Program Change TX = ON** (not factory-guaranteed).
- **Required companion: a setup check that reads/warns if Program Change TX is OFF** (and generally that MIDI Tx/Rx Sw and Receive Exclusive are ON) — silent absence of PC events otherwise looks like a bug.
- **Fallback: poll the Current/kit state** for setups where PC TX is off or the user declines to enable it.
- Note the PC number is 0-based program number (prog.1–prog.100 → PC 0–99); on the TD-50X PC is prog.1–128.

This matches the already-repo-implemented PC kit-switching path (transport exists per prior research doc) — the new work is the listener + setup-check UX for device feedback, not protocol support.
